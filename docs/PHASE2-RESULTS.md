Default database: ignored `runtime/cofre.db`, relative to the launch working directory.
The application creates exactly five tables (no ORM or extra application metadata table):

- **Grupos:** GID, exact catalog name and UI label.
- **Usuarios:** UID, email/name, GID/KID, unique bootstrap flag, required BCrypt hash,
  encrypted token BLOB, separate failure counters, blocked-until epoch milliseconds,
  access/consultation counters (all counters initially zero).
- **Chaveiro:** KID, unique UID, original encrypted private-key BLOB, canonical certificate PEM.
- **Mensagens:** all 64 exact MID/template definitions, seeded idempotently and checked on reopen.
- **Registros:** RID, epoch-millisecond timestamp, MID, nullable UID/login/file contexts.
  There is no rendered-message or credential column.

Reciprocal composite foreign keys enforce ownership of the specific UID/KID pair, not merely
existence of unrelated IDs. The bootstrap flag can only belong to group 1 and is uniquely indexed.
Read/reopen does not change registered users or reset counters. Phase 3 failure/counter behavior
is not implemented; the required persistent fields are ready for it.

## Registration and audit semantics

1. `showForm` checks bootstrap emptiness or administrator authority and records 6001.
2. `prepare` rechecks authority, records submit 6002, validates password/certificate/key,
   reads immutable snapshots, and prepares protected data without inserting an account.
3. The user confirms version, serial, validity, signature algorithm, issuer, subject, name,
   and email. Only then does the controller expose the Base32 enrollment secret.
4. Acknowledging enrollment calls commit. The account, key record, encrypted token and 6008
   accepted-confirmation record commit together. Enrollment is an acknowledgement, not a
   prematurely implemented Phase 3 token-login challenge.
5. Canceling either dialog records 6009, clears the pending material and creates no account.
   Failed registration retains editable form input; successful registration clears it.

Phase 2 audit coverage is 1001/1002/1005/1006 and applicable 6001–6010 triggers. Invalid password,
certificate/path, private-key path, wrong phrase/corrupt key and pair mismatch map to 6003–6007.
Startup phrase and key mismatch failures use applicable 6006/6007 plus 1002 and terminate.
There is no dedicated registration-success or duplicate-email MID in the specification:
6008 records accepted confirmation atomically; duplicate rejection retains the existing 6002
attempt record. No invented codes or Phase 3 session/login events are emitted.

Failure to persist an important audit record stops the operation. Injected failures show both
account/key rollback and absence of a false accepted-confirmation record. Startup/shutdown
audit errors are surfaced; administrator material is cleared even if shutdown logging fails.
